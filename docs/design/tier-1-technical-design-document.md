# Tomb Tale Online RPG: Tier 1 Technical Design Document (TDD)

## 1. Document Purpose

While the Game Design Document (GDD) explains *what* happens in the game (the rules of combat, AI behavior), this **Technical Design Document (TDD)** explains *how* the backend infrastructure makes it work. It outlines the APIs, databases, and server architecture required to support the Tier 1 MVP.

---

## 2. Global Architecture Layout

The Tier 1 MVP requires three distinct layers of technology to function securely over a network:

1. **The Game Client (Frontend)**: The engine rendering the graphics (e.g., Unity/Unreal). It sends player inputs to the server and interpolates server updates. It trusts the server completely.
2. **The Dedicated Game Server (Authoritative Instance)**: The C++/C# server running the actual physics and combat loop. It prevents players from hacking their health or damage.
3. **The Platform Backend (Microservices)**: Your existing Spring Boot services (`service-player`, `service-commerce`) that manage permanent database records.

---

## 3. Backend Requirements for Tier 1 MVP

To get players into the dungeon and fetching their correct stats, the Platform Backend must handle the following flows:

### 3.1 Authentication & Session (`Zitadel` Integration)

Before a client can even connect to the lobby, they must be authenticated.

- **Requirement**: Client passes a valid JWT token generated by Zitadel.
- **Validation**: The Auth Gateway (or `service-player` resource server) validates the PKCE flow token.

### 3.2 Player Stat Retrieval (`service-player`)

The Dedicated Game Server needs to know how much HP and Damage a player has before spawning them.

- **Trigger**: Match initiation.
- **Requirement**: The matchmaking coordinator requests the `PlayerProfile` from `service-player` (via REST or message broker like RabbitMQ).
- **Data Payload needed**: `player_id`, `base_hp`, `base_damage_modifier`.
- **Storage**: PostgreSQL / MongoDB schema for core combat stats must be defined.

### 3.3 Matchmaking / Instance Orchestration (New Component)

We need a way to group players and tell a game engine server to "start".

- **Requirement**: A lightweight Matchmaker service that receives "Find Match" requests.
- **Function**: Once 1-4 players are queued, the Matchmaker claims an available Game Server port and sends a payload: "Start Instance ID 100 on Port 7777, expecting Users [A, B]".
- **Response**: The Matchmaker sends the IP:Port of the Game Server back to the Game Clients so they can connect.

### 3.4 Message Broker Architecture (`RabbitMQ`)

Instead of direct tight-coupling, async messaging should be used for end-of-match reports.

- **Requirement**: When the Dedicated Game Server finishes a match (Win or Loss), it drops an `InstanceResultEvent` into RabbitMQ.
- **Consumer**: `service-player` consumes this event to update permanent records (e.g., total matches played, adjusting future progression tables).

---

## 4. Anti-Cheat & Security Principles

- **Never Trust the Client**: The client merely *requests* to cast a skill. The Dedicated Game Server checks if the player has enough Stamina, performs the cooldown math, and then broadcasts the success back to all clients.
- **Payload Validation**: All JSON payloads entering the Spring Boot backend from the Game Server must be strictly typed and sanitized.
