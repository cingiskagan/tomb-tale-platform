# 19. Zitadel configuration is code

- **Date:** 2026-09-18
- **Status:** accepted

## Context

Everything this platform needs from Zitadel — the project, its three roles, the
portal's OIDC client — was created by clicking in the console. Nothing recorded
what was clicked, `get-token.sh` asked a human to paste a client id, and a fresh
environment could not be reproduced. A wiped one could not be rebuilt at all.

[ADR 0018](0018-zitadel-provisions-players-and-me-is-the-fallback.md) then added
a target and an execution, which would have been two more things to click and to
remember, in the one place where forgetting fails silently.

Two of the values involved are generated by Zitadel rather than chosen by us —
the OIDC client id and the target's signing key — so they flow outward, and were
being copied by hand into `.env`, `.client-id` and `environment.ts`.

## Decision

We will create every Zitadel object from `infrastructure/zitadel-setup.sh`,
which is idempotent and talks to the REST API.

An `IAM_OWNER` service account is seeded when the instance initialises
(`ZITADEL_FIRSTINSTANCE_ORG_MACHINE_*` plus `PATPATH`), so no human mints a
credential. The script writes the generated client id and signing key back to
where they are consumed, and revokes its own token when it finishes.

## Consequences

- A wiped instance rebuilds in about a minute. That was verified by doing it —
  three times, dropping only Zitadel's schemas and leaving `player` and
  `commerce` untouched.
- Setup is one-shot per instance. Its token is revoked on success, so running it
  again needs a token supplied by hand or a rebuilt instance. Acceptable only
  because the rebuild is now cheap; it would not be otherwise.
- `IAM_OWNER` is needed for exactly one step. `ORG_OWNER` reaches projects,
  roles and clients, but Actions targets are instance-level resources. That
  single call sets the privilege of the whole script, which is why the token
  does not outlive it.
- The expiry in `.env` is a backstop, not a short window. It is an absolute date
  in a static file, so it cannot be relative to instance init; only something
  running at start-up could compute that. Until then, revocation does the work
  and the date bounds a run that dies halfway.
- Until it is revoked, the admin token sits unencrypted in a Docker volume. Fine
  on a laptop, and not the answer anywhere with a secret manager.
- The signing key turns out to be readable from the target search response, not
  only at creation. So it never has to be a permanent config value a human
  copies, and it can be rotated by deleting the target and rerunning.
- Four things the console had configured implicitly are now written down, each
  of which breaks the platform quietly when missing: `projectRoleAssertion`
  (without it no roles claim is issued and every `@PreAuthorize` denies),
  `additionalOrigins` (without it the browser is blocked by CORS), the grant
  types, and the fact that a blank PAT expiry creates an account with no token.
- `environment.ts` is patched by a script, so rebuilding shows up as a source
  diff. That is deliberate — the client id should be visible in git rather than
  known only to one laptop — but it is why serving it as runtime config is the
  next step.
- **There is no drift detection.** The script is a record of what we asked for,
  not of what is there. Anyone clicking in the console diverges from it and
  nothing notices. Terraform would catch that; a shell script cannot, and this
  is the cost of choosing one.
